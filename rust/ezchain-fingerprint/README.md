# ezchain-fingerprint — SHA-256 over canonical transaction JSON

Computes the lowercase hex SHA-256 digest of canonical JSON bytes, byte-identical
to the digests `hashlib.sha256(...).hexdigest()` produces in
`packages/core-py/src/ezchain_core/signing.py`.

## Digest contract

- **Input:** `&[u8]` — the exact canonical bytes the caller wants hashed. For a
  transaction fingerprint these are the bytes `ezchain-jsoncanon` produces,
  i.e. `json.dumps(value, sort_keys=True, separators=(",", ":"), allow_nan=False)`
  with the default `ensure_ascii=True`, or the exact raw bytes a signing
  boundary prepared.
- **Output:** 64 lowercase ASCII hex characters, no `0x` prefix, no separator,
  no trailing newline. This is precisely `ApprovedIntent.digest` and
  `PreparedTransaction.payload_digest` in `signing.py` for the same bytes.
- **No re-serialisation:** the crate accepts bytes rather than a JSON value, so
  it neither depends on nor couples to `ezchain-jsoncanon`. The caller owns
  canonicalisation; this crate owns hashing. Two different byte sequences give
  two different digests, which is the point.

```rust
use ezchain_fingerprint::fingerprint;
let canonical = br#"{"a":1}"#;
assert_eq!(
    fingerprint(canonical),
    "015abd7f5cc57a2dd94b7590f04ad8084273905ee33ec5cebeae62276a97f862",
);
```

## Why a crypto dependency is here

`sha2 = "=0.10.8"` is the **only** direct dependency, pinned to one exact
version. ADR-0052 assigns *cryptographic operations* to Rust, which authorises
this well-audited pure-Rust crate; the canon and decimal crates stayed
dependency-free because their work was not cryptographic. Transitive crates
(`digest`, `cfg-if`, `cpufeatures`, `crypto-common`, `block-buffer`,
`generic-array`, `typenum`, `version_check`) come from `sha2` alone. Hex
encoding is implemented in-crate, so no `hex` crate is added.

## Parity harness

`tests/parity_oracle.py` runs the real `ezchain_core.signing` code under the
project venv and writes `tests/parity_fixture.txt`:

- `payload_*` (6): canonical bytes from `encode_transaction(TransactionPayload)`,
  asserted equal to `PreparedTransaction.payload_digest`.
- `approval_*` (3): the canonical dict inside `ApprovedIntent.digest`, asserted
  equal to `intent.digest`.
- `kat_*` (5): raw-byte known-answer vectors from standard SHA-256 (empty,
  `abc`, short canonical JSON, binary bytes, multi-block input).

`tests/parity.rs` decodes the recorded bytes, hashes them in Rust and compares
byte-for-byte. The oracle also has independent hardcoded known-answer tests for
empty and short input in `src/lib.rs`. A failure is a parity failure: fix the
implementation and regenerate from the oracle, never edit the fixture to green.

```bash
.venv/bin/python rust/ezchain-fingerprint/tests/parity_oracle.py            # regenerate
.venv/bin/python rust/ezchain-fingerprint/tests/parity_oracle.py --check    # verify no drift
```

## Scope and safety

`#![forbid(unsafe_code)]`, no I/O, no keys, no signing, no vault, no ledger
writes and no money-path caller changed. **This is digest computation only —
not a signature.** It does not sign, does not hold key material and does not
touch a vault; live mode stays owner-blocked (ADR-0026, ADR-0035, ADR-0050
rule 3), and money arithmetic stays in Python until decimal parity is proven
(ADR-0049/0050).
